# Harness interface: contracts and explicit adapters

At the harness project root supplied with the task (the directory containing `cohort_harness/`), read `cohort_harness/contracts.py` for authoritative field schemas and the task-approved interface documents for supplied adapters. Project README files, milestone reports and other cases can contain target results: do not open them as interface documentation unless the task explicitly admits their contents. This skill may be installed outside the project, so do not infer its location from the skill's parent folders. Do not infer unavailable tools from a proposed future architecture.

## Available boundary

The original validation/source-check/freeze/verify commands never execute Agent code. Separate explicit adapters provide task-bound screened literature retrieval, generator-only WSL/bubblewrap execution, and execution-backed source replay for enrichment programs. No local execution fallback is provided. The calling environment still launches the LLM; its general file/tool access is not isolated by the generator sandbox. Generic independent target evaluation remains later work; any case-specific evaluator must keep target outcomes out of feedback.

Approved source artifacts enter through the supplied registry with their hashes. Agents may cite admitted artifacts and explicit assumptions; they must not manufacture approval records to admit their own evidence. A hash establishes which bytes were used, not their scientific truth or applicability.

## Candidate bundle

The task bundle contains its task description, allowed inputs and source registry. A candidate is placed at:

```text
<bundle>/candidates/<name>/
  evidence.json
  model_spec.json
  decision.md
  checks.json
  generator.py OR generated.csv
  source_checks.json             optional
  source_replay.json             optional execution-backed recipe
  source_contexts/*.csv          optional covariate-only source inputs
```

Submit exactly one of `generator.py` or `generated.csv`. This is an output-route choice, not a statement that either route is better. Whole-cohort, enrichment and completion tasks follow their own task-defined preservation and output requirements.

For the program route, define a top-level synchronous `generate(observed, spec, seed)` returning a pandas DataFrame. The harness will call these three arguments positionally: permitted observations (None for whole-cohort mode), the submitted model specification, and a seed. Parameter names may differ, but exactly three positional parameters and no variadic or keyword-only parameters are allowed. Use the specification for scientific settings. A deterministic construction may ignore the seed when explicitly justified. Syntax/signature acceptance does not execute the body or verify its behavior; no file/network access is part of this interface.

- `evidence.json`: admitted sources, reported statistics and scientific context.
- `model_spec.json`: model choices, parameters and evidence/assumption references.
- `decision.md`: concise rationale, applicability, unresolved limitations and stopping reason.
- `checks.json`: implementation or other checks actually performed, with their scope.
- `source_checks.json`: optional declarative checks linked to evidence items, table artifacts, operators, status and assumption references under the supported schema.

Do not place hidden reference data or their derived statistics in the bundle. The supplied-source tables for replay represent a source population; they are not target validation outcomes. If a source check needs unreported covariates or joint distributions, disclose the approximation or inability to compute it.

## Commands

Run from the project root using the configured Python environment:

```text
python -m cohort_harness validate --bundle PATH --candidate NAME
python -m cohort_harness source-checks --bundle PATH --candidate NAME
python -m cohort_harness freeze --bundle PATH --candidate NAME
python -m cohort_harness verify --bundle PATH --candidate NAME
```

For a revision:

```text
python -m cohort_harness freeze --bundle PATH --candidate NEW_NAME --parent OLD_NAME --revision FILE
```

Keep `OLD_NAME` intact. Populate the revision file according to the implemented schema and explain the actual change or no-op. Do not reinterpret changed prose as improved generated data.

`validate` checks artifact contracts. `source-checks` calculates supported source-statistic operators on supplied simulated tables. Its output explicitly leaves simulated-table provenance unverified: it does not establish that the table was generated by the submitted program. `freeze` records candidate commitments; `verify` checks recorded integrity. None of these operations certifies scientific accuracy, provides hidden-target feedback or changes the available evidence budget.

## Optional task-supplied adapters

The task must allow each literature action by its literal name, e.g. `literature.search` or `literature.fetch`. Use the sole fixed session for that bundle; budgets cover construction and revision together. A fetch can consume query budget for a screened metadata lookup. A `selection_required` response requires an explicit source version. Rejected and failed attempts remain in usage logs. Do not create registry approvals yourself.

```text
python -m cohort_harness.literature --bundle PATH search --query QUERY
python -m cohort_harness.literature --bundle PATH fetch --pmcid PMCID --version N
```

Only when execution is explicitly supplied, a controller may run a previously frozen candidate:

```text
python -m cohort_harness execute --bundle PATH --candidate NAME --run-id NEW_RUN --seed SEED --runtime CONFIG
python -m cohort_harness verify-execution --bundle PATH --run-id NEW_RUN
```

The runtime configuration is trusted controller input, not a scientific parameter. Each run has a new directory under `executions/`, preserving failures, limits, runtime information and file hashes. Read the execution status; starting a command does not prove success. An intact failed-run receipt can pass integrity verification while the recorded run remains failed. Direct-row submissions are copied and validated without executing generated code. Generator receipts do not by themselves link a source-check table to the appropriate source population or validate target scientific utility.

If a command rejects an artifact, fix its declared contract or record the limitation; do not bypass source approval or inspect hidden outcomes to make it pass. Preserve command outcomes honestly, including unsupported operators and failed checks.

## Execution-backed source feedback

For a supplied enrichment-program replay, read `docs/SOURCE_REPLAY.md` in the harness project. Put the recipe and covariate-only input files inside the candidate before freezing. Source inputs have exactly the task identifier and observed columns; generated outcomes are prohibited. The current adapter supports identity measurement mapping only; retain original reported values and explicit derivations if preparing source evidence in task units. Unsupported statistics remain unreplayed rather than relabelled.

`docs/SOURCE_CHECKS.md` defines available estimators, including explicitly typed quantiles and Spearman correlation. If a fixed-seed source portfolio is supplied, `docs/SOURCE_PORTFOLIO.md` explains its scope. These are source interfaces; validation-design and result documents belong to the evaluator. Inspect every scheduled diagnostic and any trade-offs, without interpreting repeated generator draws as new source-study evidence.

```text
python -m cohort_harness source-replay --bundle PATH --candidate NAME --replay-id NEW_ID --seed SEED --runtime CONFIG
python -m cohort_harness verify-source-replay --bundle PATH --replay-id NEW_ID --candidate NAME
```

These commands keep feedback under `source_replays/`, outside the frozen candidate. They derive source execution tasks changing only row count and declared population, execute identical code/specification, verify output linkage and recompute diagnostics. `generation_link_verified` concerns those bytes and execution; it does not verify the source-population assumptions or establish scientific validity. Large numerical discrepancies are retained feedback, not automatically execution failures.

After feedback, the builder may re-extract, revise or retain as the task allows. Bind a copy of the verified feedback in the new candidate's `checks.json` auxiliary artifacts. Keep the previous candidate intact and preserve source/target separation. The controller's target evaluator is never a generator tuning tool.
